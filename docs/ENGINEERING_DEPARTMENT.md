# Engineering Department

The Engineering Department is the first full roster of agents generated by the
Agent Factory and wired into the Runtime. All 37 agents are produced from
declarative specs (`src/departments/engineering.ts`) through the standard
factory pipeline — no agent file is hand-written.

## Generation

```bash
npx tsx src/departments/generate.ts
```

For each spec this runs the same pipeline as the CLI `generate` command:

```
blueprint → validate → save → generate → validate agent → write → register
```

Blueprints land in `blueprints/`, agent files in `.claude/agents/`, and every
agent is recorded in `registry/agents.registry.json`. Re-running is idempotent
(unchanged blueprints leave the registry untouched).

## Roster

| Sub-department | Agents |
| -------------- | ------ |
| Leadership | master-planner, solution-architect, technical-architect, project-manager, workflow-manager |
| Engineering | backend-engineer, frontend-engineer, mobile-engineer, desktop-engineer, api-engineer, database-engineer, ai-engineer, llm-engineer, integration-engineer |
| Quality | qa-engineer, test-engineer, automation-engineer, performance-engineer, security-engineer, code-reviewer, refactoring-engineer |
| Product | product-manager, ux-designer, ui-designer, documentation-engineer, prompt-engineer |
| Platform | devops-engineer, github-manager, release-manager, deployment-engineer, monitoring-engineer, cost-optimization-engineer |
| Intelligence | research-assistant, context-manager-agent, memory-manager-agent, dependency-analyzer, architecture-reviewer |

Each agent maps to a factory category template, which supplies its tool
permissions, workflow scaffold, reporting format and failure behaviour. The
spec overrides identity, role, responsibilities, objectives and the
collaboration wiring (`reportsTo` / `receivesFrom` / `sendsTo`).

## Org structure

The roster is a tree rooted at the founder:

```
founder
└── master-planner
    ├── solution-architect → technical-architect → {backend, frontend, api, database}-engineer
    ├── project-manager → workflow-manager, qa-engineer (quality), devops-engineer (platform)
    ├── product-manager → {ux, ui}-designer, documentation-engineer
    └── research-assistant
```

`reportsTo` defines escalation, `receivesFrom`/`sendsTo` define work handoff.
These compile into each generated agent's **Communication Protocol** section so
collaboration, failure propagation, retries, approvals and artifact movement are
documented in the agent itself.

## Runtime integration

One call wires the whole department into a live Runtime:

```ts
import { AgentRuntime, EventBus } from "./src/runtime/index.js";
import { loadEngineeringDepartment } from "./src/departments/index.js";

const events = new EventBus();
const runtime = new AgentRuntime({ bus: events });
loadEngineeringDepartment(runtime); // registers + activates all 37 agents
```

After this, every agent is discoverable by the **Master Orchestrator** and
addressable by every runtime service — **Event Bus**, **Shared Memory**,
**Context Manager**, **Task Queue**, **Workflow Engine**, **Artifact Manager**
and **Approval System** — by the names in the roster. Registration and
activation publish `agent.registered` / `agent.activated` on the shared Event
Bus automatically.

## Adding or changing agents

Edit `src/departments/engineering.ts`, then re-run the generator. Keep
responsibilities domain-specific so the validator's duplicate-responsibility
check stays satisfied. See [EXTENSION_GUIDE.md](./EXTENSION_GUIDE.md) for adding
new categories or tools.
