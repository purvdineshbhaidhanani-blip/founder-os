# Engineering Standards

These rules apply to every module under `src/`. They exist so that the 100th
agent generated by this factory is exactly as reliable as the 1st.

## Principles (in priority order)

1. **Infrastructure before implementation.** If you find yourself about to
   hand-write a one-off agent `.md` file, stop — add/extend a template or
   blueprint instead and let the generator produce it.
2. **Reuse before duplication.** Shared shapes live in `src/types/`. Shared
   behavior lives in `src/utils/`. If you're copying a function between two
   modules, it belongs in one of those instead.
3. **Composition before inheritance.** There are no class hierarchies in this
   codebase. Rules, templates, and validators are plain functions/objects
   composed by the orchestrating layer (CLI), not subclassed.
4. **Configuration before hardcoding.** Tool whitelists, categories, paths,
   and version numbers live in `src/constants/`, never inlined as string
   literals in logic files.
5. **Documentation before scaling.** A new phase doesn't ship without its
   corresponding section in `docs/`.

## Code conventions

- **Language:** TypeScript, strict mode, ES modules (`NodeNext`). No `any`
  without a comment explaining why it's unavoidable.
- **Validation:** All external/untrusted input (blueprint files, agent files
  read off disk) is parsed through a Zod schema or an explicit validator —
  never trusted as-typed.
- **Errors as values:** Library code (`blueprint/`, `generator/`,
  `validator/`, `registry/`) returns `Result<T, ValidationReport>` or throws
  only for truly exceptional, unrecoverable conditions (e.g. disk I/O
  failure). It does not use exceptions for expected validation failures.
  `cli/` is the boundary where a `Result` failure becomes a non-zero exit
  code and printed report.
- **No silent fallbacks.** If a blueprint is missing a required field, that's
  a validation error, not a default that papers over the gap. Defaults exist
  only for genuinely optional fields (see `.default()` usage in
  `src/types/blueprint.ts`).
- **Naming:** Agent machine names are kebab-case slugs
  (`src/utils/slug.ts::isValidSlug`). This is enforced at the schema level
  (`identity.name`), not just convention.
- **Idempotency:** Generating from the same blueprint twice produces a
  byte-identical `.md` file except for the `generatedAt` timestamp. The
  registry uses `blueprintHash` (`src/utils/hash.ts`) to detect whether a
  regeneration actually changed anything.

## Testing

- Every module that ships logic (schema, generator, validator, registry,
  templates) has a corresponding test file under `tests/`.
- Tests run against real Zod schemas and real file I/O in a temp directory —
  not mocks of our own code. Mock only true externalities (there are none in
  this repo; it's offline by design).
- A blueprint or generated agent used as a test fixture must be valid enough
  to round-trip through the real validator, not a hand-waved stub.

## Module boundaries

See `docs/ARCHITECTURE.md#layering-rules`. Code review should reject any PR
that adds an import pointing "upward" (e.g. `src/types/` importing from
`src/generator/`).
